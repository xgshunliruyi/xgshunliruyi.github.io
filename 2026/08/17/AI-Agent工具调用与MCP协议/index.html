硬核解析：AI Agent的工具调用机制与MCP协议

Sliver Eagle
2026-08-17
人工智能
AI Agent, MCP, OpenAI, Tool Calling

在上一篇文章中，我们把 Agent 定义为“模型决策、工具执行、状态与反馈闭环”的软件系统。如果继续向下追问，真正决定系统能否进入生产环境的，往往不是提示词，而是两个接口问题：模型如何把意图交给确定性程序执行，以及应用如何用统一协议连接外部能力。

前一个问题对应 Tool Calling（工具调用），后一个问题对应 Model Context Protocol（MCP）。两者经常被包装成“一句话接入工具”，但其内部包含状态机、Schema、关联标识、并发、幂等、错误语义、传输、授权与审计等一整套分布式系统问题。本文以 OpenAI Responses API 和 MCP 2026-07-28 规范为基线，从线上系统的视角拆开这些机制。

一、先划清边界：模型不会真的调用函数

Tool Calling 的本质不是把 Python 函数“塞进模型”，而是建立一种结构化协议：应用把工具的名称、说明和参数 Schema 发给模型；模型返回“希望调用哪个工具、参数是什么”的数据；应用验证后自行执行，再把结果作为新输入交回模型。

因此，模型只有提议权，运行时才有执行权。一次看起来像函数调用的过程，实际上跨过了三个信任域：

  1. 模型生成不可信的调用意图；
  2. Agent 运行时进行路由、校验、授权、审批与调度；
  3. 工具服务在自己的安全边界内执行，并返回不可信的外部数据。

MCP 位于更下一层。它不规定模型如何推理，也不要求 Host 使用某一家模型 API；它规定 Host 内的 Client 如何发现并调用一个 Server 暴露的 Tools、Resources 和 Prompts。可以用下面这张表避免概念混淆：

层次 主要问题 典型数据 不负责什么
Tool Calling 模型如何表达动作意图 工具名、JSON 参数、call_id、工具结果 不执行代码，不自动授权
Agent Runtime 谁能执行、何时执行、如何循环 状态、策略、审批、预算、幂等记录 不替工具实现业务规则
MCP Host 如何标准化连接外部能力 JSON-RPC、tools/list、tools/call、Schema 不判断工具是否可信、是否该调用
Tool Service 动作具体如何完成 数据库查询、第三方 API、事务结果 不应相信模型传入的身份或权限

这两个结论贯穿全文：Schema 合法不等于业务语义正确；协议互通不等于安全可信。

二、Responses API 的工具调用状态机

1. output 是异构事件流，不是“一条助手消息”

Responses API 的 response.output 是一个数组。数组项可能是 message、function_call、推理相关 item、工具搜索 item，或其他受支持类型。生产代码不能假设 output[0] 就是文本，也不能只读取 output_text 后丢掉其余 item。

  • id 标识这个 output item；
  • call_id 标识一次逻辑工具调用，后续 function_call_output 必须用它关联结果。

工具运行结束后，应用追加的不是普通 user message，而是专门的输入 item：

output 通常是字符串，可以承载 JSON、错误码或普通文本；图片和文件另有对应内容类型。它是模型下一轮观察到的数据，而不是 API 对真实函数返回类型的承诺。

完整循环应实现为状态机，而不是写死“两次请求”：

  1. 将用户输入、指令和工具定义发送给模型；
  2. 保存本次 response.output 的全部 item；
  3. 若存在一个或多个 function_call，逐个做解析、校验、授权与执行；
  4. 为每个调用追加同 call_id 的 function_call_output；
  5. 带上完整历史再次请求模型；
  6. 没有工具调用且产生最终 message 时结束，否则继续循环；
  7. 达到轮数、时间或费用上限时由运行时强制终止。

“完整回放”非常重要。对推理模型，只保存自然语言消息或只保存工具调用，会丢失模型返回的其他状态 item，造成上下文不连续。在服务端保存了前一次响应、且数据政策允许时，应用也可以用 previous_response_id 串联响应；若使用 store=false、Zero Data Retention 或自行管理历史，则应原样保留每轮 output item，包括加密的 reasoning item，而不是把它们重新改写成一段文本。

response.status="completed" 也只表示这一轮模型响应完成，不代表 Agent 任务已终止。反过来，incomplete 中的 output_text 可能只是因 max_output_tokens 截断的半句话，必须在执行任何调用前检查 status、error 与 incomplete_details。

2. 一轮可能有零个、一个或多个调用

模型可以直接回答，也可以同一轮产生多个 function_call。运行时必须把“多个”当作正常路径，而不是异常边界。并行只适用于彼此独立、没有副作用冲突的调用，例如同时读取两张互不相关的订单。下面几类调用不应盲目并行：

  • 后一个参数依赖前一个结果；
  • 两个调用可能修改同一资源；
  • 任一调用需要人工审批；
  • 工具存在严格的速率限制或事务顺序；
  • 部分成功会留下难以补偿的外部状态。

设置 parallel_tool_calls=false 可以让一轮至多产生一个函数调用，但这只是缩小模型输出空间，不能替代服务端锁、事务和幂等控制。允许并行时，应为每个调用单独记录状态，并在全部结果可用后一次性回传；如果某个调用失败，其他调用已经成功，就必须返回每项的独立结果，不能用一个笼统的“批次失败”抹掉事实。

三、工具 Schema 是协议，不是装饰

1. strict 到底保证什么

在 Responses API 中，函数工具通过 JSON Schema 描述参数。启用 strict: true 后，模型生成的参数会可靠地符合受支持的 Schema 子集。严格模式要求每一层对象都设置 additionalProperties: false，并把 properties 中的字段全部列入 required。

如果业务上允许字段缺省，不应把它简单地从 required 删除；严格模式下应让模型显式传 null：

严格模式解决的是结构约束：字段是否存在、类型是否正确、枚举是否越界。它不证明以下命题：

  • order_id 确实存在；
  • 当前用户拥有该订单；
  • 这个订单现在允许退款；
  • 模型选择查询订单而不是查询物流是正确的；
  • 参数来自用户授权，而不是网页中的提示注入；
  • 即将执行的动作仍与审批时展示的动作一致。

所以工具入口仍要像公网 API 一样做校验。身份、租户、角色和授权范围应由认证上下文注入，不能让模型填写 user_id 或 is_admin。即便参数通过了 Schema，工具也必须重新检查对象级权限和当前业务状态。

2. 工具描述直接影响路由质量

模型选择工具依赖名称、描述、参数说明和当前任务。get_data、run_action 这类宽泛接口会把大量隐含分支推给模型；更好的设计是窄职责、可验证语义和明确失败条件，例如：

  • get_order：只读、按订单号查询当前用户的订单；
  • preview_refund：只计算可退金额，不产生副作用；
  • commit_refund：使用审批令牌提交退款，要求幂等键。

不要让模型填写运行时已经知道的字段，也不要把总是连续执行且不可分割的两个内部步骤暴露成两个工具。工具越多，名称越相似，路由混淆和上下文成本越高。工具定义会计入输入 token，因此大规模工具面需要按任务动态缩小。

3. tool_choice 是可调用集合，不是权限系统

OpenAI API 提供多种选择策略：

配置 含义 适合场景
"auto" 模型可不调用、调用一个或多个工具 一般对话与检索
"required" 必须调用至少一个工具 答案必须来自实时系统
指定函数 必须调用指定工具 已由确定性路由选定动作
"none" 本轮禁止调用工具 汇总或只读解释阶段
allowed_tools 从已传入工具中限制本轮可调用子集 分阶段开放能力、保持提示缓存稳定

allowed_tools 能降低误选概率并减少暴露面，但不能作为最终授权。攻击者可能绕过模型直接请求工具服务，模型也可能在被允许的工具内构造越权参数。真正的权限必须在运行时和工具服务端执行。

五、生产运行时：真正困难的是失败语义

1. 不要把所有失败都叫 exception

工具运行时至少要区分四类结果：

类别 例子 应对策略
参数或业务失败 订单不存在、状态不可退款 返回稳定错误码，允许模型修正或解释
瞬时失败 连接重置、限流、短暂不可用 有界退避重试，服从服务端重试提示
永久系统失败 配置错误、接口版本不兼容 立即停止该路径并告警
结果未知 请求超时，但下游可能已经提交 先查幂等记录或操作状态，禁止直接重放

“结果未知”最危险。假设支付服务完成扣款后，响应在网络中丢失。客户端看到超时，并不意味着操作失败；立即重试可能二次扣款。正确做法是携带幂等键，超时后通过查询接口确认最终状态。对于没有幂等能力的第三方系统，应把动作放入带持久状态的作业队列，并明确进入人工处置，而不是让模型猜测。

错误信封应面向恢复逻辑，而不是直接暴露堆栈：

工具端记录完整异常，模型只看到最小、脱敏、可行动的信息。错误信息本身也可能来自数据库或第三方，不能未经转义就拼进系统提示词，更不能把访问令牌、SQL、内部主机名和堆栈交给模型。

2. 超时、取消与背压要逐层传播

模型请求、工具队列、工具自身和下游 HTTP 都要有独立 deadline。外层取消时，应向下游传播取消信号；但对于已经越过提交点的副作用，取消只代表“不再等待”，不代表动作被撤销。运行时应记录 cancel_requested、commit_started、commit_confirmed 等状态，而不是一个模糊的 cancelled。

并发还需要背压：限制单个 run 的并发工具数、单用户并发数、全局队列长度和下游连接池。模型一次吐出二十个调用不构成突破配额的理由。超过预算时返回明确错误或暂停，而不是无限排队。

3. 审批必须绑定不可变动作

敏感工具应拆成“预览”和“提交”两阶段。预览返回人类可读摘要以及规范化动作的哈希；用户批准的是具体对象、金额、收件人和版本，而不是一句泛化的“允许退款”。提交时携带短期审批令牌，服务端重新计算哈希并核对：

这可以防止 TOCTOU（检查时与使用时不一致）：审批后订单状态可能变化，或模型可能偷偷换参数。提交端必须重新读取资源、校验版本和权限；若状态变化，令牌失效并要求重新预览。审批 UI 应展示规范化后的最终参数，而不是模型自然语言摘要。

4. 幂等记录必须跨越整个副作用窗口

线上系统往往同时存在四层重试：模型循环重试、Agent 运行时重试、任务队列重试和下游 HTTP Client 重试。若每层都独立重试三次，一次故障理论上可能放大为数十次真实调用。应指定唯一的重试所有者，并把其他层限制为传输级、明确没有到达服务端的失败；对限流和过载，尊重 Retry-After，加入抖动，并设置整个 run 的重试预算。

写工具的幂等表至少包含：租户、授权主体、工具版本、幂等键、规范化参数哈希、执行状态、资源版本、最终结果和过期时间。状态不应只有成功/失败两个值，而应能表达：

收到相同幂等键时，若参数哈希相同且已有 COMMITTED 结果，直接重放已保存的结果；若正在 EXECUTING，返回可查询的 operation handle，而不是并发再执行；若键相同但参数哈希不同，返回 IDEMPOTENCY_CONFLICT。进入 UNKNOWN 后只能向权威系统对账，不能把“不知道”擅自改写为“失败”。

“规范化参数”也比 sort_keys=True 更复杂。金额要统一最小货币单位，Unicode 要统一规范形式，默认值要显式展开，时间要固定时区和精度，资源引用要带版本。否则 299、299.0 与字符串 "299.00" 可能产生不同哈希，或两个语义不同的动作被错误合并。幂等键还要绑定授权主体；用户 A 的键不能命中用户 B 的结果。

跨多个外部系统无法依靠本地数据库事务获得“恰好一次”。更现实的是持久化状态机加补偿：先记录意图，再执行每个步骤，逐项保存不可变回执；后续步骤失败时，根据业务规则补偿已成功步骤或转人工。工具结果应明确列出每个子动作的 succeeded、failed、unknown，模型只能据此解释，不能用自然语言把部分成功包装成全部成功。

只读调用也存在一致性语义。订单服务刚完成退款，读副本可能仍返回旧状态。工具定义应说明数据时间戳、来源和一致性级别；涉及后续写入时，提交端必须对主存储重新校验版本。缓存读取适合回答“当前已知状态”，不适合作为高风险动作的唯一前置条件。

5. 轨迹可观测性与评测

一条工具轨迹至少应关联 run_id、response_id、call_id、工具名、参数摘要、授权主体、策略结果、审批 ID、开始/结束时间、重试次数、结果码和 token 用量。原始参数与结果可能含个人信息，应按字段脱敏并设置短于业务数据的日志保留期。

评测不能只看最终文本“像不像正确答案”。生产回归集要覆盖：

  • 正确选择工具与不该调用工具时保持静默；
  • 参数精确性、对象级权限与租户隔离；
  • 并行调用的依赖顺序与部分失败；
  • 超时、重复响应、过期审批和未知执行结果；
  • 工具结果中的提示注入与恶意 URL；
  • 达到轮数或费用上限时是否停止；
  • 轨迹是否以最少调用完成目标。

可分别计算工具选择准确率、参数字段准确率、非法调用拦截率、重复副作用率、任务成功率、P95 工具延迟和每任务成本。只有最终答案正确但中途越权读取了数据，仍然是失败样例。

六、大工具集：Tool Search 与程序化调用

当工具数达到几十甚至几百个时，把全部 Schema 放进每轮上下文会增加 token、延迟和误选概率。OpenAI 的 Tool Search 允许先把部分工具标记为延迟加载，模型检索到相关工具后再加载定义；当前文档要求使用支持该能力的 gpt-5.4 或更新模型。加载以后仍按普通 function_call 处理，授权边界也不改变。

Programmatic Tool Calling 则允许模型生成一段受控程序，在托管运行时中调用合资格工具并压缩中间结果。要启用它，请求需加入 programmatic_tool_calling 工具，并用每个工具的 allowed_callers 明确允许 programmatic 调用。托管运行时执行生成的 JavaScript，但 client-owned 工具仍由应用执行：程序内层 function_call 带有 caller，应用返回 function_call_output 时必须原样回传 call_id 与 caller；外层 program / program_output 则用程序自己的 call_id 关联。

它适合边界明确的过滤、连接、排序、去重和聚合；如果每个结果都会改变下一步语义判断、动作需要审批，或必须保留原始引用，则应使用直接工具调用。程序少了模型往返，并不意味着结果自然更可靠，仍要同时评测 program_output 与最终 message。

二者解决的是上下文规模与编排效率，不是权限问题。延迟加载的工具在真正可调用前仍应经过任务级 allowlist；程序化环境也必须有调用次数、并发、CPU、时间、网络和副作用限制。

七、MCP 的架构：标准化的是连接，不是智能

MCP 采用 Host—Client—Server 架构：

  • Host 是承载模型与用户体验的应用，创建多个 Client，决定连接权限、用户授权、上下文聚合和跨 Server 编排；
  • Client 由 Host 创建，并且每个 Client 只与一个 Server 通信，负责协议版本、能力、请求路由和隔离；
  • Server 暴露聚焦的 Tools、Resources 与 Prompts，可以是本地进程，也可以是远程服务。

Server 不应看到整段对话，也不应看见其他 Server 的数据。Host 只把完成当前调用所需的参数交给它。这个隔离原则很重要：若把完整聊天记录、所有检索文档和其他连接器的结果无差别发送给 Server，采用 MCP 也不会自动形成安全边界。

八、2026-07-28：MCP 已经是无状态协议

这是当前规范与大量旧教程差异最大的地方。MCP 2026-07-28 删除了 initialize / notifications/initialized 握手和协议级会话，也删除了 Streamable HTTP 的 Mcp-Session-Id。每个请求都是自包含的，携带协议版本与 Client capabilities；Client identity 应随请求提供。Server 必须实现 server/discover，但 Client 是否预先调用它是可选的：Client 也可以直接调用任意 RPC，并在版本不支持时处理 UnsupportedProtocolVersionError。

维度 2025-11-25 及更早旧版 当前 2026-07-28
启动 initialize 后发送 notifications/initialized 无初始化握手
版本与能力 连接建立时协商 每个请求在 _meta 中自描述
HTTP 会话 可用 Mcp-Session-Id 绑定会话 该请求头已删除
能力发现 初始化结果 Server 必须实现 server/discover，Client 可选调用

GET/SSE 恢复 曾有独立 GET 与恢复机制 GET 和 Last-Event-ID 恢复已删除

兼容 SDK 仍可能先探测现代协议，在发现旧 Server 后回退到 initialize。这不代表 initialize 仍属于 2026-07-28；它只属于 dual-era 实现的 legacy 路径。新实现不应在现代请求中发送或依赖 Mcp-Session-Id。

无协议会话并不等于业务不能有状态。购物篮、浏览器上下文或数据库事务应由 Server 创建显式 handle，例如 basket_id，后续作为普通工具参数传回。handle 应不透明、有过期时间，并在每次使用时重新验证调用者权限。对认证服务，handle 是资源名称而不是授权凭据；拿到别人的 handle 不应获得访问权。

3. isError 与 JSON-RPC error 是两层错误

MCP 明确区分协议错误和工具执行错误：

  • 工具不存在、请求结构畸形或协议内部异常，使用 JSON-RPC error；
  • 参数值不合法、上游 API 失败、业务规则拒绝等可供模型修正的问题，返回正常 result，并设置 isError: true。

桥接到模型时，两者都要转换成有限、脱敏的工具观察，但运维指标不能混为一谈。大量 -32602 可能是 Client/Server 版本或目录缓存错误；大量 ORDER_NOT_FOUND 可能只是用户输入问题。错误分类决定告警对象和重试策略。

MRTR 是协议往返机制，不应被直接等同于 Host 的安全审批。恶意 Server 完全可以伪造“请确认上传密钥”的 elicitation。Host 必须先判断这个输入请求是否与用户目标和已授予权限一致，再决定如何向用户呈现；高风险动作仍使用 Host 自己的审批策略。

十一、两种标准传输：stdio 与 Streamable HTTP

1. stdio

stdio 适合本地 Server。Host 启动子进程，Client 向其 stdin 写入一行一个 JSON-RPC 消息，从 stdout 读取响应。消息本身不能包含未转义换行；Server 的 stdout 只能写协议消息，日志必须写 stderr。否则一条调试输出就足以破坏 framing。

取消请求时，Client 发送引用 JSON-RPC ID 的 notifications/cancelled。子进程退出会丢失所有在途请求；因为现代协议没有隐藏会话，Client 可以重启进程并按照工具幂等语义决定是否重试。环境变量中的凭据只应注入该进程所需的最小集合，避免把 Host 的全部环境原样继承过去。

2. Streamable HTTP

Streamable HTTP 使用单一 MCP endpoint，每条消息是一个新的 POST。Server 可以返回单个 JSON，也可以为该请求返回 SSE 流，在最终响应前发送与请求相关的进度通知。当前版本删除了独立 GET stream 和 SSE Last-Event-ID 恢复；流断开意味着在途响应丢失，重发必须使用新的 JSON-RPC ID，并遵守业务幂等规则。

HTTP 请求必须同时接受 application/json 和 text/event-stream，携带 MCP-Protocol-Version 与 Mcp-Method；tools/call、resources/read、prompts/get 还需携带 Mcp-Name。Header 是为网关路由和观测镜像的元数据，Body 才是事实来源。Header 与 Body 中的版本、方法、名称或 x-mcp-header 参数不一致时，Server 必须拒绝，而不能任选其一。

x-mcp-header 允许 Server 在工具 inputSchema 的原始类型字段上声明一个镜像名，Client 调用时把对应参数复制到 Mcp-Param-{Name}，便于负载均衡器或 WAF 不解析 JSON 就路由。例如 region 可映射为 Mcp-Param-Region。这不是把参数从 Body 移走：两处值必须一致，缺失或冲突应返回 HeaderMismatch。非 ASCII、控制字符以及首尾空白要按规范的 Base64 sentinel 编码。密码、Token 和个人信息不应使用该扩展，因为 Header 更容易进入代理与访问日志；网关也不能只检查 Header 后忽略 Server 对 Body 的最终校验。

Server 还必须校验 Origin 以防 DNS rebinding；本地 HTTP Server 应只绑定 127.0.0.1，而不是默认监听 0.0.0.0。关闭某个请求的 SSE 响应流表示取消该请求，但同样不保证已经提交的副作用被撤销。

十二、MCP 授权：Token 必须绑定目标资源

MCP 的 HTTP 授权规范基于 OAuth 2.1；授权本身对所有 MCP 实现是可选的，但一旦为 HTTP Server 提供授权，就应遵循规范。stdio 不走这套 HTTP OAuth 流，通常从隔离后的环境取得凭据。

远程 MCP 的关键不是“有 Bearer Token”就够了，而是 Token 必须绑定正确的资源：

  1. Client 通过 Protected Resource Metadata 发现授权服务器；
  2. 授权请求与换取 Token 的请求都带 resource，其值是 MCP Server 的规范 URI；
  3. 每个 HTTP 请求使用 Authorization: Bearer ...，不得把 Token 放进查询字符串；
  4. Server 验证 Token 的真实性与有效性（例如验证 JWT 签名或内省 opaque token）、有效期和 scope，并确认自己就是预期 audience / resource；
  5. Token 不能被透传或接受为其他服务的凭据；Server 调下游时应换取或使用专属于下游的凭据。

最小权限不仅是缩短 scope 列表。Host 应按用户、Server 和任务分别保存授权，写 scope 在需要时 step-up，完成后不继续向模型暴露相应工具。Client identity 和 Server identity 都是自报元数据，只能用于展示、日志与调试，不能作为认证依据。

此外，MCP Server 本身属于供应链。工具名、描述、annotations、图标 URL、返回文本和资源链接全部可能恶意。Host 应做到：

  • 连接前展示 Server 来源、发布者和请求的权限；
  • 默认只开放经过审核的 Server 与工具子集；
  • 把 annotations 当提示，不把 readOnlyHint=true 当安全证明；
  • 在调用前展示敏感参数，阻止将密钥、Cookie 或其他 Server 数据外传；
  • 校验返回 Schema、大小、MIME、URL 域名和重定向；
  • 对每个 Server 设置独立超时、速率、网络出口和日志策略。

下面的独立示例固定使用官方 mcp==2.0.0。MCPServer 从类型注解生成输入 Schema，从 Pydantic 返回模型生成 outputSchema；Client(mcp) 直接在内存中连接，适合单元测试，不启动端口，也不发送模型请求。

十四、把 MCP 工具桥接进模型时该做什么

一个可靠桥接器不会把 tools/list 原样复制给模型然后盲转结果，而应形成明确管线：

  1. 对 Server 做信任登记并建立独立 MCP Client；
  2. 分页读取工具目录，按授权过滤，并处理跨 Server 重名；
  3. 将 MCP inputSchema 转成模型函数工具 Schema，保留来源映射；
  4. 模型产生 function_call 后，先做本地策略、参数和审批校验；
  5. 分配新的 JSON-RPC ID，记录它与 call_id、trace 的映射；
  6. 执行 tools/call，验证 outputSchema、大小与内容安全；
  7. 把成功或错误规范化为 function_call_output，继续模型循环。

跨 Server 重名不能依赖 serverInfo.name，因为它不保证全局唯一。Host 可以使用自身登记 ID 构造模型可见名称，如 crm__search_customer，同时维护到 (server_id, original_tool_name) 的不可伪造映射。不要允许模型直接填写目标 Server URL。

目录缓存也必须绑定授权主体、scope 和 cacheScope。用户 A 获得的工具集合不能作为公共缓存交给用户 B；权限降级时必须主动失效。调用时仍要重新鉴权，因为“目录里曾经出现过这个工具”不是当前权限证明。

最后，MCP 工具结果与网页内容一样是不可信输入。Host 可以保留原始结果用于审计，但送进模型前应限制体积、剥离不需要的富媒体、标记来源，并阻止结果中的指令提升权限。模型说“Server 要求你调用另一个写工具”只是一段数据，不是授权链。

十五、上线前检查清单

如果一个 Agent 将要连接真实工具，务必认真逐项检查：

  • 工具是否窄职责，输入和输出是否都有可验证 Schema；
  • 用户身份是否来自认证上下文，而不是模型参数；
  • 是否为每个 run 设置轮数、时间、并发、token 与费用预算；
  • 是否完整保存 output item，并正确关联 call_id；
  • 读取操作是否去重，写操作是否有持久业务幂等键；
  • 未知结果是否先查询状态，而不是立即重放；
  • 审批是否绑定规范化参数、资源版本和有效期；
  • 工具错误、协议错误和系统错误是否具有不同指标；
  • MCP Client 是否分页、按授权缓存并处理工具目录变化；
  • 现代 MCP 请求是否自描述，且没有误用旧版 Session；
  • HTTP Header 与 Body 是否一致，Origin、OAuth audience 和 scope 是否验证；
  • stdio Server 是否只在 stdout 输出协议消息；
  • Server 描述、annotations、返回内容与 URL 是否都按不可信输入处理；
  • 轨迹评测是否覆盖越权、注入、超时、重复和部分成功。

结语

工具调用不是模型拥有了一双“手”，而是模型向运行时提交了一份结构化动作提案。可靠性来自提案之后的确定性系统：Schema 缩小语法空间，授权确认主体能做什么，审批绑定具体副作用，幂等抵御重试，状态机约束循环，追踪与评测让错误能够被发现。

MCP 也不是万能工具层。它把 Host 与外部能力之间的发现、调用、传输和授权接口标准化，使不同模型应用和工具服务能够组合；但 Server 是否可信、工具是否该开放、结果是否能进入模型，始终是 Host 的责任。把 Tool Calling 与 MCP 放在各自正确的层次，Agent 才会从“能跑的演示”成长为可审计、可限制、可恢复的生产系统。
