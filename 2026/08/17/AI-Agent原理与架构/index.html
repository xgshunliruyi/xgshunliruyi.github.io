详解：AI Agent的原理、架构与核心技术

Sliver Eagle
2026-08-17
人工智能
AI Agent, OpenAI, 大语言模型

大语言模型擅长理解和生成内容，但一次模型调用通常只是“输入文本，输出文本”。当系统能够围绕目标持续获取信息、选择工具、执行动作，并根据结果调整下一步时，它才开始具备 Agent 的形态。更准确地说，AI Agent 是以模型为决策策略、工具为执行器、状态与反馈闭环为运行机制的软件系统。

这一定义把注意力从“模型有多聪明”转向“整个系统如何可靠地完成任务”。本文从通用原理出发，拆解 Agent 的运行循环、分层架构与核心技术，再以 OpenAI Agents SDK 展示一个最小实现，并讨论安全、评测以及不该使用 Agent 的场景。

一、Agent 不等于大语言模型

几个经常混用的概念，可以通过“谁决定下一步”来区分：

形态 核心能力 下一步如何确定
大语言模型（LLM） 根据上下文生成内容 单次推理结束即停止
聊天机器人 在多轮对话中封装模型 通常由用户继续提问
固定工作流（Workflow） 按预设步骤调用模型或程序 由代码中的流程图、规则决定
AI Agent 感知状态、选择动作并根据反馈迭代 由模型与运行时约束共同决定

例如，“收到简历后依次抽取字段、校验格式、写入数据库”是一条固定工作流，即使其中使用了 LLM，也不必称为 Agent。若系统需要先判断岗位类型，再自主选择检索人才库、比较要求或请求补充材料，并根据工具返回结果改变计划，它才具有明显的 Agent 特征。

因此，Agent 不是一个神秘的新模型，而是一种系统设计。模型提供带概率的决策能力，普通代码负责状态、权限、重试、超时和停止条件，工具负责真正影响外部世界。三者缺一不可。

二、Agent 的基本原理：一个受控的反馈循环

可以把一次运行抽象为状态 $s_t$、决策策略 $\pi$ 与动作 $a_t$：

$$a_t \sim \pi(\text{goal}, s_t, \text{context}, \text{tools})$$

环境执行动作后返回观察 $o_{t+1}$，运行时再用它更新状态，得到 $s_{t+1}$。这个循环通常包含五个处理步骤和两个控制结果：

  1. 观察（Observe）：接收用户目标、历史消息、工具结果以及环境事件。
  2. 组装上下文（Contextualize）：检索相关资料，裁剪历史，把规则、可用工具与当前状态放进模型上下文。
  3. 决策（Decide）：模型选择回答、调用工具、委派给其他 Agent，或请求用户确认。
  4. 行动（Act）：运行时校验参数与权限，再执行函数、API、浏览器或代码环境。
  5. 反馈（Feedback）：把成功结果或结构化错误送回循环，必要时重试、换工具或重规划。
  6. 暂停（Pause）：需要人工审批或补充输入时保存运行状态，条件满足后恢复同一次运行。
  7. 终止（Stop）：目标已完成、超过步数或预算、出现不可恢复错误或被策略拦截时停止。

关键点是：循环属于 Agent 运行时，而不是模型本身。模型可以提出动作，但运行时才拥有执行权。可靠系统必须设置最大轮数、超时、令牌或费用预算、重复调用检测和明确的完成条件；否则一个看似合理的“继续尝试”就可能变成无限循环。

三、从模型到生产系统：分层架构

1. 模型与指令：决策层

模型承担意图理解、任务分解、工具选择和结果综合。系统指令应描述目标、边界、完成标准与失败时的行为，而不是堆砌互相重复的规则。模型越强并不意味着系统越可靠：它仍可能误解上下文、选择错误工具或产生不受证据支持的结论，所以关键决定要由外部策略验证。

2. 运行时控制器：控制层

控制器维护循环与状态机，解析模型输出，调度工具，处理异常、重试、流式输出、暂停和恢复。这里适合使用确定性代码实现不可妥协的约束，例如“转账前必须审批”“同一幂等键不得重复扣款”“最多调用工具八次”。不要把这类规则只写在提示词里。

3. 上下文与记忆：状态层

上下文窗口是本轮模型可见的信息，记忆则是应用保存并按需取回的信息，两者不是一回事。常见设计包括：

  • 工作记忆：当前计划、已完成步骤和最近的工具结果；
  • 会话记忆：同一任务中的消息与状态，支持暂停后恢复；
  • 长期记忆：经过授权保存的用户偏好、历史事实或知识索引。

记忆写入应有来源、时间和作用域，读取时进行权限过滤与相关性排序。盲目塞入全部历史既会增加成本，也会让过期信息干扰决策；自动总结同样可能丢失关键约束，因此重要状态应以结构化字段单独保存。

4. 工具与环境：执行层

工具把“生成文字”变成“查询订单、运行代码、发送消息”等可验证动作。每个工具都应有清晰名称、窄职责、参数模式、返回模式和错误语义。输入符合 JSON Schema，只能说明格式正确，不能证明订单属于当前用户、日期合法或该动作值得执行；业务校验必须留在工具服务端。

环境则定义动作发生的位置，如数据库、浏览器、容器或第三方 SaaS。高风险环境应隔离文件系统和网络、限制凭据与执行时间，并将只读工具和写工具分开授权。

5. 安全、可观测性与评测：横切治理层

这三类能力不应作为上线前才添加的“外挂”。每次运行都要能回答：模型看到了什么、为什么选择这个工具、参数是什么、策略是否放行、结果如何以及耗时和资源消耗多少。日志要关联同一条 trace，同时对密钥、个人信息和工具返回内容做脱敏。

四、构成 Agent 的核心技术

ReAct：让推理与行动交替发生

ReAct 论文提出让推理与任务动作交错：模型根据当前观察决定动作，外部结果又成为下一步依据。工程价值不在于输出冗长的“思维过程”，而在于把任务拆成可检查的行动轨迹。生产系统应记录工具选择、输入输出和简短决策摘要，不应依赖或要求暴露模型的隐藏推理。

Tool Calling 与结构化输出：建立机器可执行的接口

Tool Calling 让模型从工具集合中选择函数并生成结构化参数；结构化输出则约束最终结果的字段和类型。它们把自然语言与程序接口连接起来，减少脆弱的文本解析。然而，结构正确不等于语义正确。参数仍需类型之外的业务校验，执行结果仍需检查，副作用操作仍需授权和幂等保护。

RAG：按需取得外部知识

RAG 原始论文将参数化模型与外部非参数记忆结合。在 Agent 中，检索通常是一个工具或上下文组装步骤：先召回文档，再让模型基于证据回答。它有助于引入新知识和来源，但不会自动消除幻觉。索引是否新鲜、召回是否完整、文档是否可信、回答是否忠于证据，都要分别评测；重要结论还应显示引用或返回“证据不足”。

MCP：统一连接上下文与工具

Model Context Protocol 规范（2026-07-28）定义了 Host、Client、Server 之间的标准通信方式，Server 可暴露 Resources、Prompts 和 Tools。MCP 降低了不同 Agent 应用重复适配数据源与工具的成本，但它只解决互操作接口，不替应用决定某个服务是否可信。Host 与 Client 仍需按各自职责落实身份授权、能力协商、用户同意、最小权限和结果校验：Host 控制连接权限与用户授权，Client 维护与单个 Server 的隔离通信。

反思、重规划与多 Agent

当工具失败或新证据推翻假设时，Agent 可以总结差距并重规划；这种“反思”应由明确触发条件控制，例如关键校验失败，而不是无上限地要求模型继续改进。多 Agent 则把研究、执行、审查等职责拆给不同角色，可通过 handoff 转交控制权，或由协调者并行调用专家。

拆分只有在子任务边界清楚、上下文可隔离、并行确实节省时间时才有价值。否则，多一层 Agent 就多一份提示词、状态同步、延迟和失败路径。单 Agent 加几个边界清晰的工具，往往是更好的起点。

六、安全：把不可信输入与执行权限隔开

Agent 同时处理自然语言和真实权限，主要风险也来自二者相遇：

  • 提示注入：网页、文档和工具结果都应视为不可信数据，不能覆盖系统策略；对高风险动作重新核验原始用户意图。
  • 越权调用：按用户、任务和工具实施最小权限，写操作使用短期凭据，不把通用管理员密钥放入模型上下文。
  • 不可逆副作用：展示动作对象与影响，等待人工批准；使用幂等键、事务或可撤销方案，避免重试造成重复执行。
  • 代码与网络风险：在沙箱中限制目录、网络目标、CPU、内存和运行时长，输出也要经过大小与敏感信息检查。
  • 失控循环：限制轮数、并发、重试、令牌与费用预算；连续出现相同错误时停止并向用户说明阻塞点。

Guardrail 适合自动检查输入、输出或工具调用，审批适合由人决定敏感动作是否继续。二者不能互相替代：自动规则减少常见错误，人类确认承担高影响决策。

七、评测：不要只看最终回答像不像

传统问答常以最终文本评分，但 Agent 还必须评估过程。建议从真实任务中建立包含正常、模糊、冲突、工具失败和攻击输入的数据集，并持续记录：

  • 任务完成率与最终答案的事实性、完整性；
  • 工具选择、参数、调用顺序和停止时机是否正确；
  • RAG 引用是否支持结论，证据不足时是否拒绝猜测；
  • 权限策略、审批和敏感信息处理是否符合要求；
  • 总轮数、延迟、令牌、工具成本和失败恢复能力。

模型输出具有随机性，关键样例应重复运行，比较分布而非单次结果。每次修改模型、提示词、工具说明或路由策略，都应回放同一套回归集。调试阶段先检查完整 trace，稳定后再使用 graders 和批量 eval；OpenAI 的 Agent 评测文档也将工具选择、handoff 与安全策略纳入端到端轨迹评估。

八、什么时候不应该使用 Agent

Agent 的优势是处理路径事先难以穷举的任务，代价则是不确定性、延迟、成本与更大的安全面。以下场景通常应优先使用确定性工作流：

  • 步骤固定、规则明确，例如表单校验、账务计算和数据库迁移；
  • 动作不可逆且错误容忍度极低，但又无法安排审批；
  • 一次查询或单次模型调用已经可以完成目标；
  • 需要稳定的毫秒级延迟、严格吞吐量或可形式化证明的结果；
  • 缺少可观测性、沙箱、权限系统与代表性评测集。

实际系统可以采用混合架构：让工作流掌握主路径和关键控制点，只在分类、非结构化信息理解或异常处理等局部环节调用模型；等评测证明动态决策确有收益，再逐步扩大 Agent 的权限和范围。

结语

理解 Agent 的最好方式，不是把它想象成“会自主思考的聊天机器人”，而是把它看成一个由概率决策器驱动、由确定性运行时约束的反馈控制系统。模型决定可能的下一步，工具连接真实世界，状态让任务得以延续，权限与评测则决定它是否值得被信任。

从一个目标明确、工具只读、轮数受限的单 Agent 开始，先让每一步可观察、可阻断、可验证，再谈长期记忆与多 Agent 协作，通常是通往生产可用系统最稳妥的路径。
